# 작업지시서: 추천 말씀에서 동행 연결까지 v1

> 설계 문서: `docs/design/connected-companion-experience-v1.md`
> 우선순위: HIGH
> 목표: 시나리오의 `말씀 → 나 → 과거의 나 → 행동 → 필요한 사람 → 서로 도움` 루프를 직관적인 화면과 안전한 동의 흐름으로 구현한다.

## 작업 원칙

- 한 화면에 사용자가 해야 할 일은 하나만 둔다.
- 반응만 남겨도 완료로 처리한다.
- AI 추천은 설명 가능한 후보 제안이며 자동 연결이 아니다.
- 원문과 연락처는 양쪽 동의 전까지 공개하지 않는다.
- 기존 `ReviewReport`, `ReflectionEntry`, `ActionStep`, `PastEncounter` 계약을 깨지 않는다.

## S1. 추천 말씀과 과거 기록을 하나의 장면으로 통합

**대상:** `src/app/today/page.tsx`, `src/app/j/[slug]/page.tsx`, `src/components/today/today-card.tsx`

- 기록이 없으면 랜덤/결정적 랜덤 성구를 먼저 표시한다.
- 기록이 있으면 가장 적절한 과거 기록의 한 줄과 추천 성구를 하나의 narrative block으로 보여준다.
- “왜 이 말씀이 나왔나요?”에는 실제 연결 신호만 사용한다.
- 과거 기록의 당시 성구를 상세 보기에서 함께 열 수 있게 한다.
- 기존 기록·추천 성구·반응·다음 성구의 상태 전이를 테스트한다.

**완료 조건:** 사용자가 첫 화면에서 “지난번 기록 → 오늘 추천 말씀” 관계를 한 번에 이해한다.

## S2. 반응 후 선택 기록 모달과 다음 성구

**대상:** `src/components/today/today-card.tsx`, `src/components/today/reaction-modal.tsx`, 관련 테스트

- 세 반응 클릭 후 모달을 연다.
- 모달에서만 선택 한 줄 기록을 허용한다.
- `다음 성구 보기`는 현재 카드를 종료하고 다음 후보를 표시한다.
- 입력하지 않고도 모달을 닫을 수 있다.
- 반응별 완료 문구를 구분한다.
- 기존 inline 입력, Tiny Action의 기본 노출을 제거한다.

**완료 조건:** 반응 후 사용자가 숙제를 받지 않고 다음 화면으로 이동할 수 있다.

## S3. 동행 프로필과 공개 범위

**대상:** `prisma/schema.prisma`, `src/app/me/settings`, 신규 동행 컴포넌트/API

- `CompanionProfile` 추가: `enabled`, 공개 태그, 한 줄 소개, 도움 가능 범위.
- 기본값은 비활성·비공개.
- 원문·민감 정보·AI 추정 상태를 프로필에 저장하지 않는다.
- 프로필 수정·비활성화·미리보기 UI를 제공한다.
- 동행 AI 처리 동의는 기존 성구 개인화 동의와 별도 상태로 저장한다.
- 비활성화 시 미전송 후보와 대기 중 요청의 처리 결과를 사용자에게 안내한다.

**완료 조건:** 사용자가 어떤 정보가 동행 후보에게 보이는지 이해하고 직접 켜고 끌 수 있다.

## S4. AI 동행 후보 생성

**대상:** `src/lib`, `src/app/api`, 동행 설계 테스트

- 사용자 동의와 충분한 기록 조건을 먼저 확인한다.
- 후보는 허용된 프로필 집합에서 최대 3명까지 선택한다.
- 후보별 `reasonSummary`, `signalLabels`, `supportingEntryIds`를 저장한다.
- 내부 점수와 프롬프트 원문은 사용자에게 노출하거나 DB에 저장하지 않는다.
- 근거가 부족하면 후보를 만들지 않고 “아직 적절한 연결을 찾지 못했어요”로 종료한다.
- AI 실패 시 자동 연결하지 않고 재시도/폴백 상태를 저장한다.
- 후보 생성 범위는 동의한 공간·그룹·프로필로 제한한다.
- `supportingEntryIds`는 서버 내부에서만 접근하고 클라이언트에 전달하지 않는다.
- 모델 입력·결과 캐시의 보관 기간과 철회 시 삭제를 구현한다.
- 후보별 역할(`peer`, `guide`, `group_member`)과 요청 수신 가능 여부를 검증한다.
- 사용자와 상대방에게 보여주는 이유 문장을 분리한다.
- 기록 원문의 지시문·링크·타인 개인정보를 데이터로만 처리해 prompt injection을 차단한다.
- 매칭은 사용자가 직접 시작할 때만 실행하며, 회고·추천 성구 완료 뒤 자동으로 후보를 노출하지 않는다.
- 매칭 시작 전 도움 방식·공개 범위·대상 범위를 한 단계에서 선택하게 한다.

**완료 조건:** 모든 후보가 “왜 도움이 될 수 있는지”를 실제 사용자 신호와 공개 프로필에 근거해 설명한다.

## S5. 수락·거절·나중에 보기 상태 머신

**대상:** `prisma/schema.prisma`, 동행 API/UI

- `CompanionCandidate`, `CompanionDecision`, `CompanionConnection` 추가.
- 사용자 결정: `accepted`, `rejected`, `snoozed`.
- 상대방 결정 전에는 `pending_counterparty`.
- 양쪽 수락 후에만 `connected`.
- 거절은 상대방에게 사유·사용자 상태를 전달하지 않는다.
- 같은 후보는 일정 기간 재추천하지 않는다.
- 요청 철회, 후보 만료, 상대방 부재, 중복 요청을 정의하고 멱등 처리한다.
- 모든 상태 변경은 현재 상태 조건부 업데이트로 경쟁 요청을 흡수한다.
- 상대방에게는 앱 내부 알림함으로만 요청을 전달하며, 외부 알림은 별도 동의가 필요하다.
- 양쪽 수락 후에도 첫 접촉은 중계 메시지로 시작하고 연락처 공개는 별도 확인을 받는다.
- 수락 후 빈 채팅 화면 대신 검토 가능한 첫 인사 선택지를 제공하고 자동 전송하지 않는다.
- 상대의 무응답을 사용자 실패나 미달성 상태로 표시하지 않는다.

**완료 조건:** 수락·거절·나중에 보기 각각의 다음 화면과 저장 상태가 명확하다.

## S6. 안전·종료·신고

**대상:** 동행 UI/API, 기존 `SafetyReport` 활용

- 연결 후 차단·신고·연결 종료를 항상 제공한다.
- 차단 시 양쪽에서 서로 숨긴다.
- 신고 내용과 상대방 노출 정보를 분리한다.
- 위기·학대·의료·법률 문제를 AI 매칭으로 처리하지 않는다.
- 민감 신호는 일반 동행 후보 생성에서 제외한다.
- 후보 생성·요청·메시지 전송 rate limit과 일일 상한을 둔다.
- 연령·취약성 정보가 불명확한 경우 일반 매칭을 보수적으로 제한한다.
- 직접적인 위기 도움 요청은 일반 매칭이 아닌 안전 안내 흐름으로 보낸다.

**완료 조건:** 사용자가 언제든 연결을 중단할 수 있고, 상대 정보가 안전하게 차단된다.

## S7. 도움을 주는 사용자로의 전환

**대상:** 프로필 설정, 동행 후보 화면

- 도움을 받은 사용자에게도 공개 태그 기반으로 도움 제공 여부를 선택하게 한다.
- 원문 자동 공개 없이 한 줄 소개와 도움 가능 범위만 공개한다.
- 도움 제공 상태를 별도 토글로 관리한다.
- 역할과 가능 범위를 선택 목록으로 제한하고 상담·치료·목회 권위를 암시하는 표현을 금지한다.

**완료 조건:** 사용자가 수혜자와 제공자 역할을 모두 자발적으로 선택할 수 있다.

## S8. 회고와 동행 연결

**대상:** `src/components/review/*`, `src/app/lookback/[id]`

- 회고의 “지금의 모습” 또는 마지막 영역에 동행 제안을 연결한다.
- 회고 내용을 매칭 입력으로 재사용할 때도 AI 동의와 최소 데이터 원칙을 적용한다.
- 회고 화면에서 동행·기도·행동을 동시에 숙제로 노출하지 않는다.

**완료 조건:** 회고에서 발견한 자기 이해가 필요한 사람과의 안전한 연결로 자연스럽게 이어진다.

## 검증 계획

- `bunx tsc --noEmit`
- 관련 단위 테스트: 추천 선택, 반응 저장, 동행 상태 머신, 접근 제어, 거절 재추천 억제
- `bun test tests/`
- `bun run build`
- E2E: 신규/기존 사용자, 기록 있음/없음, 반응 후 기록/스킵, 후보 수락/거절/상대 거절/차단
- UX 수동 검증: 360px, 768px, 1440px에서 첫 화면의 주 CTA와 다음 상태가 즉시 이해되는지 확인
- 동시성 검증: 양쪽 수락 경쟁, 한쪽 철회와 수락 경쟁, 중복 요청, 만료 직전 요청
- 개인정보 검증: 원문·entry ID·연락처가 동의 전 응답·로그·클라이언트 상태에 없는지 확인
- 폴백 검증: AI timeout, 유효하지 않은 후보, 후보 없음, 반복 성구, 동의 철회

## 우선순위 판정

- S1·S2는 즉시 사용자 경험 개선 범위다.
- S3 이전에는 AI 매칭을 구현하지 않는다.
- S4는 동의·근거·안전 테스트가 준비된 뒤에만 실행한다.
- S5·S6이 완료되지 않으면 실제 사람 간 연결을 활성화하지 않는다.

## QA 게이트

- [ ] 추천 실패 시 안전 성구가 표시되고 빈 화면이 없다.
- [ ] 반응 후 기록 없이 `다음 성구 보기`로 종료할 수 있다.
- [ ] 저장 실패한 반응이 완료 상태로 표시되지 않는다.
- [ ] 새로고침 후 이미 응답한 카드의 모달이 자동 재노출되지 않는다.
- [ ] `DailyCheckIn.oneLine`과 `PastEncounter.note`가 서로 바뀌지 않는다.
- [ ] 매칭 이유가 사용자 신호와 후보의 공개 프로필에 근거한다.
- [ ] 사용자가 직접 매칭을 시작하기 전에는 후보가 노출되지 않는다.
- [ ] 수락 후 첫 메시지가 자동 전송되지 않는다.
- [ ] 수락 전 원문·연락처·민감 상태가 노출되지 않는다.
- [ ] 사용자 거절은 상대에게 전달되지 않는다.
- [ ] 양쪽 수락 전 `connected` 상태가 되지 않는다.
- [ ] 차단·신고·종료 후 재노출이 차단된다.
- [ ] AI 매칭 동의 철회 후 새 생성과 기존 미연결 후보가 중단된다.
- [ ] 상태 전이와 경쟁 요청 테스트가 모두 통과한다.
