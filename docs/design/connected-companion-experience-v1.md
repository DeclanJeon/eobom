## 1. 제품 정의

이어봄은 묵상 과제를 관리하는 앱이 아니다. 사용자가 먼저 말씀을 받고, 자신이 남긴 행동과 마음을 시간이 지난 뒤 다시 만나며, 그 과정에서 자신을 더 입체적으로 이해하고 필요한 사람과 안전하게 연결되는 프로그램이다.

핵심 문장:

> 추천 말씀을 먼저 받고, 나의 반응과 행동을 기억하고, 그 기억으로 나를 배우며, 필요한 사람과 서로 돕는다.

제품 루프:

```text
말씀 수령
→ 선택적 반응
→ 선택적 한 줄/행동 기억
→ 과거의 나 재회
→ 나의 반복·변화 인지
→ 필요한 사람 추천
→ 수락/거절로 동행 결정
→ 도움을 주고받음
```

## 2. 절대 원칙

1. **말씀 먼저**: 첫 화면의 주인공은 추천 성구다.
2. **기록은 선택**: 반응만 남겨도 경험은 끝난다. 입력창과 행동 목록을 기본 노출하지 않는다.
3. **숙제 없음**: 미완료, 스트릭, 점수, 평가, 반복 알림으로 압박하지 않는다.
4. **연결은 판정이 아님**: AI는 “당신에게 이 사람이 필요하다”고 단정하지 않고, “이 사람이 이런 이유로 도움이 될 수 있어요”라는 제안만 한다.
5. **사람 연결은 양방향 동의**: 추천받은 사람의 수락과 사용자의 수락이 모두 있기 전에는 개인 연락처·원문·상태를 공개하지 않는다.
6. **도움의 방향은 양방향**: 사용자는 도움을 받는 사람에만 머물지 않고 자신의 경험으로 다른 사람에게 도움을 제안할 수 있다.
7. **AI는 거울이지 재판관이 아님**: 진단, 영적 권위, 심리 판정, 관계 단정, 치료 약속을 출력하지 않는다.
8. **프라이버시 우선**: 원문 기록은 기본 비공개이며, 매칭에 전달하는 데이터는 동의한 최소 요약과 신호뿐이다.

## 3. 첫 화면 정보 구조

첫 화면의 순서는 반드시 `추천 성구 → 선택적 과거 맥락 → 반응`이다. 과거 기록이 있더라도 과거 카드가 추천 성구를 밀어내지 않는다. 과거 기록은 추천의 이유를 이해시키는 짧은 맥락이고, 오늘의 성구가 주인공이다.

### 3.1 기록이 없는 사용자

```text
오늘 여기까지 온 당신에게
[추천 성구]
오늘은 그냥 받아가도 괜찮아요.
[반응 3종]
```

반응 후에는 모달만 연다.

```text
[선택] 왜 마음에 남았나요?
[기록 남기기] [다음 성구 보기]
```

### 3.2 기록이 있는 사용자

성구만 보여주거나 과거 기록만 별도 카드로 분리하지 않는다. 하나의 연결 장면으로 보여준다.

```text
지난번의 내가 남긴 기록
“나 요즘 너무 조급한 것 같다.”

오늘은 이 말씀을 함께 읽어볼까요?
[추천 성구]
왜 이 말씀이 왔는지: 최근 기록의 주제와 연결된 이유
[반응 3종]
```

과거 기록의 원문 전체는 기본 노출하지 않는다. `기록 전문 보기`를 눌렀을 때만 상세로 이동한다.

### 3.3 추천 성구 규칙

- 기록 0~2개: 승인된 코퍼스에서 결정적 랜덤 선택
- 기록 3개 이상이며 AI 처리 동의가 있음: 최근 기록의 주제·감정·질문을 최소 요약해 AI 후보를 요청
- AI 실패·근거 부족·동의 없음: 안전한 결정적 랜덤 폴백
- 추천 이유는 실제 기록 신호에 근거해야 하며, “하나님이 지금 주신 말씀” 또는 진단 문구는 금지
- 최근 동일 장·노출 성구는 억제한다.

### 3.4 추천 성구의 상태와 실패 처리

추천은 사용자에게 보이는 카드 상태와 내부 생성 상태를 분리한다.

```text
requested → selected → displayed
                    ├─ skipped → next_requested
                    ├─ reacted → completed
                    └─ error → safe_random_fallback
```

- 로딩 중에는 빈 카드나 스피너 대신 마지막으로 확정된 안전한 성구를 유지한다.
- AI 응답 지연·실패·유효성 검증 실패 시 즉시 승인 코퍼스의 결정적 랜덤 성구를 표시한다.
- `다음 성구 보기`는 현재 카드와 다른 `cardKey`를 만들고, 같은 장·같은 범위·최근 노출 후보를 제외한다.
- URL의 index는 무한히 후보를 소비하지 않도록 서버에서 상한을 두고, 범위를 넘으면 새 세션 seed로 순환한다.
- 추천 이유가 없거나 기록 근거가 불충분하면 “당신에게 필요한 말씀”이 아니라 “오늘 함께 읽을 말씀”으로 표시한다.
- 성구 수령은 카드가 표시된 시점에 완료된다. 반응·기록·다음 성구는 모두 선택이다.
- 사용자가 브라우저를 새로고침해도 이미 반응한 카드의 모달을 자동으로 다시 열지 않는다. 같은 카드의 반응은 현재 선택을 수정할 때만 다시 열 수 있다.
- `다음 성구 보기`는 사용자 세션에서 본 후보를 서버 또는 서명된 세션 상태로 추적한다. 단순 클라이언트 index만 신뢰하지 않는다.

## 4. 반응 후 흐름

반응은 하루 경험을 거의 끝내는 확인 동작이다.

| 반응 | 저장 | 모달 기본 문구 | 선택 후속 |
|---|---|---|---|
| 다시 읽었어요 | 반응만 저장 | 다시 읽은 마음을 기억해둘게요. | 한 줄 기록 또는 다음 성구 |
| 아직 마음에 남아요 | 반응만 저장 | 아직 마음에 남는다는 걸 기억해둘게요. | 한 줄 기록 또는 다음 성구 |
| 지금은 다르게 보여요 | 반응만 저장 | 지금 다르게 보인다는 걸 기억해둘게요. | 무엇이 달라졌는지 한 줄 또는 다음 성구 |

`다음 성구 보기`는 현재 경험을 종료하고 다음 추천 후보를 보여준다. 사용자가 기록하지 않았다는 이유로 동일 화면에 남겨두지 않는다.

반응 저장 성공과 모달 표시는 분리한다. 저장이 실패하면 모달에서 재시도할 수 있고, 저장되지 않은 반응을 완료한 것처럼 표시하지 않는다. 모달의 닫기·뒤로가기·`다음 성구 보기`는 모두 정상 종료이며, 어느 것도 추가 입력을 요구하지 않는다.

한 줄의 목적도 분리한다.

- 오늘의 성구에 대한 한 줄: `DailyCheckIn.oneLine`
- 과거 기록을 다시 만난 뒤의 변화 메모: `PastEncounter.note`

두 값은 같은 텍스트처럼 보이더라도 서로 다른 기억 사건이다. 과거 기록 카드에서 `지금은 다르게 보여요`를 선택하면 변화 메모를 `PastEncounter.note`에 저장하고, 오늘의 성구에서 남긴 한 줄은 새 quick 기록으로 연결한다.

## 5. 기억과 자기 이해

### 5.1 기억 단위

- 기록 원문과 작성일
- 당시 연결된 성구
- 사용자의 반응
- 선택적으로 남긴 한 줄
- 선택적으로 만든 행동/기도
- 시간이 지난 뒤의 재방문 반응

### 5.2 사용자에게 보여줄 표현

좋은 표현:

- “지난번의 내가 이런 마음을 남겼어요.”
- “그때의 말씀과 지금의 마음을 나란히 볼까요?”
- “최근 기록에서 이런 흐름이 반복되어 보여드렸어요.”

금지 표현:

- “당신은 불안형입니다.”
- “당신에게 반드시 이 사람이 필요합니다.”
- “AI 분석 결과 당신의 문제는 관계입니다.”

### 5.3 자기 이해 화면

`/lookback/[id]`의 Mirror Narrative를 중심으로 다음 세 층을 유지한다.

1. 관찰: 사용자의 기록에서 실제로 반복·변화한 내용
2. 근거: 연결된 기록 날짜와 짧은 인용
3. 질문: 사용자가 스스로 분별할 질문

사용자는 관찰 문구를 `나와 맞아요`, `잘 모르겠어요`, `다르게 보여요`로 정정할 수 있다. 정정은 실패나 평가로 기록하지 않고 다음 추천·회고의 참고 신호로만 사용한다. 근거가 하나뿐이거나 상충 기록이 많으면 단정형 문장을 만들지 않고 “이런 흐름도 보였어요”로 낮춘다.

점수, 등급, 성격 유형, 진단명은 노출하지 않는다.

### 5.4 행동 기억

행동은 사용자가 직접 선택했을 때만 기억한다. 화면은 행동을 새로 요구하지 않고, 이미 선택한 행동을 다음 재방문에서 조용히 확인한다.

```text
행동 제안(선택)
→ 사용자가 수락
→ 실행 여부를 묻지 않고 종료 가능
→ 다음 재방문에서 “그때 남긴 행동을 돌아볼까요?”(선택)
→ 결과 한 줄 또는 건너뛰기
```

행동 상태는 `suggested`, `accepted`, `reflected`, `dismissed`로 제한한다. `overdue`, `실패`, `미달성` 같은 압박 상태를 기본 UI에 사용하지 않는다. 결과가 없다는 사실도 자기 이해의 근거로 단정하지 않는다.

## 6. 필요한 사람 AI 매칭

동행 매칭은 자동으로 튀어나오는 다음 숙제가 아니다. 사용자가 회고나 말씀을 통해 “사람과 이야기해보고 싶다”를 직접 선택했을 때만 시작한다. `지금은 혼자 머물기`, `나중에`, `사람을 만나보고 싶어요`를 동등한 선택지로 둔다.

### 6.1 매칭 대상

초기 버전은 공개 커뮤니티 전체를 자동 검색하지 않는다. 사용자가 명시적으로 연결 허용한 사람, 함께 공간에 있는 사람, 또는 검수된 동행 프로필만 후보가 된다.

후보 프로필은 다음처럼 최소화한다.

- 표시 이름 또는 익명 별칭
- 함께할 수 있는 주제/경험 태그
- 도움을 줄 수 있는 방식
- 응답 가능 범위와 시간
- 공개 허용된 한 줄 소개
- 신고·차단 상태

매칭 대상은 `CompanionProfile.enabled = true`이고, 현재 사용자의 공간·그룹·명시적 초대 범위에 속하며, 차단·신고·휴면·연결 한도를 통과한 프로필로 제한한다. 공개 프로필이 없거나 매칭 가능한 사람이 없으면 사람을 억지로 추천하지 않고 “아직 연결할 사람을 찾지 못했어요”로 종료한다.

연락처, 사적 원문, AI 추정 상태, 민감한 신앙·건강 정보는 매칭 후보에 전달하지 않는다.

### 6.2 매칭 결과 형태

AI는 후보를 최대 3명까지 제안한다.

```text
이 사람이 도움이 될 수 있는 이유
- 당신의 최근 기록에 나타난 “혼자 감당하려는 마음”과
  이 사람의 공개된 동행 주제 “함께 계획 세우기”가 연결돼 있어요.
- 실제 도움을 약속하는 판정이 아니라, 대화를 시작해볼 수 있는 후보입니다.
```

반드시 포함:

- 연결 근거 1~2개
- 근거가 된 사용자 신호의 범위
- AI가 모르는 것
- “도움이 될 수 있음”이라는 불확실성
- 수락·거절·나중에 보기 버튼

후보 카드의 `supportingEntryIds`는 서버 내부 근거 연결에만 사용한다. 클라이언트로 원문 ID를 보내거나 상대에게 전달하지 않는다. 사용자가 보는 근거는 비식별화한 신호 라벨과 사용자가 이미 공개한 범위의 짧은 설명으로 재구성한다.

금지:

- 내부 점수
- 순위 경쟁
- 운명적·영적 확정 표현
- 상대방에게 사용자의 원문 자동 전달
- 수락 전 직접 연락처 노출

### 6.3 매칭 상태 머신

```text
candidate
  ├─ user_rejected → rejected
  ├─ user_later → snoozed
  └─ user_accepted → pending_counterparty
        ├─ counterparty_rejected → declined
        ├─ counterparty_expired → expired
        └─ counterparty_accepted → connected
              ├─ either_blocked → blocked
              └─ either_ended → ended
```

추가 전이:

```text
candidate → expired
pending_counterparty → withdrawn
snoozed → candidate
connected → counterparty_unavailable → ended
```

- 모든 전이는 서버에서 소유권·현재 상태를 다시 확인하고 멱등적으로 처리한다.
- 요청에는 만료 시각과 재추천 억제 기간을 둔다.
- 어느 한쪽도 동의하지 않은 상태에서는 연결된 것으로 세지 않는다.
- 사용자는 상대방이 결정하기 전 요청을 철회할 수 있다.

상대방에게 요청을 전달하는 방법은 앱 내부 알림함으로 제한한다. 이메일·푸시·외부 메신저 연락은 별도 수신 동의 없이는 사용하지 않는다. 상대방은 요청을 받은 이유와 공유 예정 범위만 보고, 요청자의 원문이나 AI 추정 상태는 볼 수 없다.

공개 매칭만 사용하는 경우에도 `pending_counterparty`를 거치며, 한쪽의 수락만으로 연결 완료 처리하지 않는다.

### 6.4 수락

사용자가 `수락`하면 다음을 확인한다.

1. 어떤 정보가 상대에게 공유되는지
2. 어떤 정보는 계속 비공개인지
3. 상대 수락 전에는 익명·중계 메시지만 가능한지
4. 연결을 언제든 종료할 수 있는지

상대가 수락하기 전 상태:

```text
연결 요청을 보냈어요.
상대가 수락하기 전까지 기록 원문과 연락처는 공개되지 않아요.
```

양쪽 수락 후:

- 서로 공개 허용한 프로필만 표시
- 원문은 별도 공유 동작 없이는 공개하지 않음
- 대화·기도·동행 기록은 별도 동의로 시작

수락 확인 화면은 공유 항목, 비공개 항목, 상대 수락 전 상태, 연결 종료 방법을 한 화면에서 보여준다. 수락 API는 중복 요청을 흡수하고, 상대방이 이미 거절·차단·만료한 경우 연결을 만들지 않는다.

### 6.5 거절

거절은 실패나 평가가 아니다.

```text
이번에는 연결하지 않을게요.
이 선택은 상대에게 이유와 함께 전달되지 않아요.
```

거절 직후:

- 같은 후보를 일정 기간 재추천하지 않음
- 사용자의 거절 사유는 선택적으로만 수집
- 이유는 매칭 품질 개선용 집계 데이터로만 사용
- 거절 사유는 사용자별 장기 프로필이나 AI 원문 프롬프트에 재사용하지 않는다.
- 상대에게 “거절당함” 또는 사용자의 상태를 알리지 않음

선택 가능한 내부 사유:

- 지금은 사람과 연결할 때가 아님
- 주제가 맞지 않음
- 이미 함께할 사람이 있음
- 이유를 남기지 않음

### 6.6 안전장치

- 차단은 즉시 적용하고 양쪽 화면에서 상대를 숨긴다.
- 신고는 연결 상태와 무관하게 가능하다.
- 미성년자·취약 사용자·위기 신호는 일반 매칭에서 제외하고 별도 안전 안내로 보낸다.
- AI가 위기, 자해, 학대, 의료·법률 문제를 판단하거나 상담자를 가장하지 않는다.
- 후보 생성과 연결 완료를 분리해 AI 오류가 자동 연락으로 이어지지 않게 한다.
- 매칭 전·후 모두 사용자 차단 목록을 우선 적용한다.
- 동일 사용자의 반복 요청, 후보 생성, 메시지 전송에는 rate limit과 일일 상한을 둔다.
- 프로필 작성자는 언제든 동행 가능 상태를 끄고 진행 중 요청을 철회할 수 있다.
- 앱이 연령·취약성 정보를 알 수 없는 경우 일반 매칭을 보수적으로 제한하고, 공개 커뮤니티 연결이 아닌 안전한 도움 안내로 보낸다.
- 후보에는 역할 범위를 붙인다: `peer`(비슷한 경험을 나누는 사람), `guide`(검수된 동행자), `group_member`(같은 공간의 사람). 역할을 상담사·목회자·치료자로 오인하게 표시하지 않는다.
- 연결 후 첫 접촉은 목적·기대 범위가 적힌 중계형 인사로 시작한다. 외부 연락처 교환은 양쪽의 별도 확인 후에만 허용한다.

### 6.7 AI 매칭의 데이터 수명과 동의

- AI 처리 동의는 매칭 기능을 켜기 전에 별도 확인한다. 기존 성구 개인화 동의와 묶지 않는다.
- 동의 화면에는 입력 데이터 종류, 목적, 보관 기간, 철회 방법을 명시한다.
- 원문은 기본적으로 모델 입력에서 제외하고, 필요한 경우 한시적 요약 생성에만 사용한 뒤 폐기한다.
- 사용자가 동의를 철회하면 새 후보 생성을 즉시 중단하고, 생성된 미연결 후보·근거 캐시는 삭제 또는 비활성화한다.
- 연결된 상대에게 이미 공개된 프로필 정보는 연결 종료 시 더 이상 새로 노출하지 않지만, 법정 보존이 필요한 안전 사건을 제외한 활동 로그는 삭제 정책을 따른다.

### 6.8 위기·부적합 매칭

AI가 위기 가능성을 확정하지 않는다. 다만 사용자가 직접 위기 도움을 요청하거나 안전 규칙에 걸리면 일반 동행 후보를 보여주지 않고, 즉시 도움 요청·신뢰할 사람에게 연락·지역 전문기관 안내 중 하나를 선택하게 한다. 이 경로는 매칭 성공률에 포함하지 않는다.

### 6.9 후보 품질과 노출 제한

- 후보 생성은 최소 기록 수와 최소 공개 프로필 수를 모두 만족해야 한다.
- 후보가 없는 것이 정상인 경우가 있으며, 시스템은 임의 후보를 채우지 않는다.
- 동일 후보·동일 이유를 반복 노출하지 않는다.
- 사용자가 보는 “매칭 이유”와 상대가 보는 “요청 이유”는 서로 다른 최소 문장으로 생성한다.
- 사용자 기록에 포함된 지시문·링크·타인의 개인정보는 AI 입력에서 제거하거나 데이터로만 취급한다(prompt injection 방지).
- 생성된 이유가 프로필의 공개 태그와 사용자 신호를 연결하지 못하면 후보를 폐기한다.

### 6.10 매칭 시작 전 사용자 선택

사용자가 매칭을 시작하기 전에 다음을 직접 선택한다.

- 원하는 동행 방식: 경험을 나누기 / 함께 기도하기 / 현실적인 조언 듣기 / 같은 공간의 사람 만나기
- 공개할 범위: 주제 태그만 / 익명 한 줄 포함 / 이미 공개한 기록만
- 대상 범위: 같은 그룹 / 검수된 동행자 / 허용된 전체 후보

선택하지 않은 범위는 후보 생성에 사용하지 않는다. 선택 화면은 짧은 한 단계로 끝내며, 선택하지 않고도 말씀 경험을 완료할 수 있다.

### 6.11 연결 이후의 실제 사용 흐름

연결 완료 후 빈 채팅 화면을 던지지 않는다.

```text
연결 완료
→ 첫 인사 문장 3개 중 하나 선택 또는 직접 작성
→ 상대에게 중계 전달
→ 답변 대기 또는 종료
```

첫 인사는 자동 전송하지 않는다. 사용자가 확인한 뒤 전송한다. 답변이 없다고 실패·미응답으로 표시하지 않으며, 일정 시간이 지나면 조용히 종료하거나 다시 보기를 선택하게 한다.

## 7. 도움을 주는 사용자로의 전환

사용자가 자신의 기록을 통해 도움을 받은 뒤, 공개 가능한 경험 태그를 선택하면 다른 사용자에게 “도움을 줄 수 있는 사람”으로 제안될 수 있다.

기본값은 항상 비활성이다.

```text
내 경험을 누군가에게 도움이 될 수 있는 주제로 열어둘까요?
[열어두기] [나중에]
```

열어둘 때도 원문이 아니라 사용자가 고른 태그·한 줄 소개·가능한 범위만 공개한다.

## 8. 데이터 모델 방향

현재 `User`, `ReflectionEntry`, `PastEncounter`, `ActionStep`, `ReviewReport`를 유지하고 다음 모델을 추가한다.

- `CompanionProfile`: 사용자가 공개 동행 가능 여부와 허용 태그를 관리
- `CompanionCandidate`: 특정 사용자에게 생성된 후보와 근거 요약
- `CompanionDecision`: 사용자의 수락·거절·나중에 보기 결정
- `CompanionConnection`: 양쪽 동의가 완료된 연결
- `CompanionSafetyEvent`: 차단·신고·종료 이력

각 모델에 필요한 공통 필드:

- `createdAt`, `updatedAt`
- 상태 변경용 `version` 또는 조건부 업데이트 기준
- 사용자별 접근 스코프
- 만료·삭제 시각
- 감사 추적용 전이 이벤트

권장 최소 계약:

```text
CompanionProfile
  userId, enabled, role, topicTags, helpModes, intro,
  availability, acceptsRequests, consentVersion, disabledAt

CompanionCandidate
  requesterId, profileId, status, reasonSummary,
  signalLabels, supportingEntryIds(internal), expiresAt,
  generatedAt, modelVersion

CompanionDecision
  candidateId, userId, decision, reasonCode, decidedAt

CompanionConnection
  candidateId, requesterId, counterpartyId,
  status, requesterAcceptedAt, counterpartyAcceptedAt,
  endedAt, endedBy
```

`role`, `topicTags`, `helpModes`, `reasonSummary`는 허용 목록과 길이 제한을 적용한다. 자유 텍스트를 그대로 후보 검색 조건이나 AI 시스템 지시문으로 사용하지 않는다.

`CompanionDecision`은 사용자별로 후보당 한 건만 존재해야 하며, `CompanionConnection`은 동일한 두 사용자 쌍에 중복 연결을 만들 수 없다. 신고·차단 이벤트는 상대방에게 사유를 노출하지 않는다.

AI 원문 프롬프트나 원문 묵상은 후보 테이블에 저장하지 않는다. `reasonSummary`, `signalLabels`, `supportingEntryIds`처럼 최소 근거만 저장한다.

## 9. 화면 계약

### 오늘/묵상기록지

- 첫 화면 주인공은 추천 성구
- 기존 기록이 있으면 추천 성구와 연결된 기억으로 함께 보여줌
- 반응 전에는 기록 입력·행동 목록을 숨김
- 반응 후 모달에서만 기록 또는 다음 성구 선택

### 회고

- 기록의 반복과 변화를 근거와 함께 보여줌
- 회고의 마지막에는 `오늘의 말씀`, `기도`, `작은 행동`, `동행 제안` 중 실제 데이터가 있는 것만 표시
- 다음 행동을 여러 개 동시에 요구하지 않음

### 동행

- 후보마다 “왜 이 사람이 도움이 될 수 있는지”가 먼저 보임
- `수락`, `거절`, `나중에 보기`는 동등하게 접근 가능
- 연결 전 개인 정보 노출 없음
- 연결 후 `연결 종료`, `차단`, `신고`를 항상 찾을 수 있음
- 첫 접촉은 중계 메시지로 시작하며, 외부 연락처 공개는 별도 동의

## 10. 성공 조건

- 첫 진입 후 추천 성구 도달률 95% 이상
- 반응 후 강제 입력 없이 화면을 떠날 수 있음
- 기존 기록 사용자에게 과거 기록과 추천 성구의 연결 이유가 보임
- 매칭 이유를 사용자가 이해할 수 있음
- 수락·거절 후 다음 상태가 명확함
- 자동 매칭으로 연락처나 원문이 노출되지 않음
- 사용자가 도움을 받는 경험과 도움을 제공하는 경험이 모두 선택적으로 가능함

측정 조건:

- 추천 성구 표시 성공률과 안전 폴백 비율을 분리 측정한다.
- 반응 후 `기록 남기기`와 `다음 성구 보기` 중 하나로 이동할 수 있는 비율을 측정한다.
- 매칭 이유 이해도는 “왜 이 사람이 제안되었는지 이해했다” 단일 질문으로 측정한다.
- 수락 후 실제 연결 완료율과 상대 거절·만료율을 분리한다.
- 신고·차단은 성공률을 높이는 지표로 사용하지 않고 안전 지표로 별도 관리한다.

## 12. QA 보완 판정

초안에서 발견된 주요 구멍과 보완 결과:

| QA 항목 | 초안의 구멍 | 보완 |
|---|---|---|
| 추천 실패 | AI 지연·실패·중복 처리 부재 | 상태 머신, 결정적 안전 폴백, 중복 억제 추가 |
| 다음 성구 | index 무한 증가·동일 성구 반복 가능 | 서버 상한·새 seed·cardKey 규칙 추가 |
| 자기 이해 | AI 관찰을 사용자가 수정할 수 없음 | 사용자 정정과 상충 근거 처리 추가 |
| 매칭 범위 | 누구를 검색하는지 불명확 | 동의한 공간·프로필·차단 상태로 제한 |
| 근거 노출 | supportingEntryIds가 개인정보가 될 수 있음 | 내부 전용으로 제한 |
| 수락/거절 | 철회·만료·중복 요청 부재 | 전이·멱등성·만료 추가 |
| AI 동의 | 성구 개인화 동의와 구분되지 않음 | 매칭 별도 동의·철회·보관 정책 추가 |
| 안전 | rate limit·연령 불명·위기 경로 부재 | 보수적 제한·신고·차단·위기 분기 추가 |
| 성공 기준 | 정성적 문구만 존재 | 표시·이해·연결·안전 지표 분리 |

2차 QA에서 추가로 확인한 구멍:

| QA 항목 | 위험 | 보완 |
|---|---|---|
| 첫 화면 위계 | 과거 기록이 추천 성구를 밀어낼 수 있음 | 성구를 주인공으로 고정하고 과거 기록은 맥락으로 제한 |
| 반응 완료 | 저장 실패인데 완료처럼 보일 수 있음 | 저장 성공과 모달 표시를 분리하고 재시도 허용 |
| 새로고침 | 이미 응답한 카드가 다시 모달을 열 수 있음 | 응답 상태와 모달 상태 분리 |
| 다음 성구 | 클라이언트 index 조작·반복 가능 | 서버/서명 세션 추적과 후보 억제 |
| 메모 의미 | 오늘 한 줄과 과거 변화 메모가 섞임 | `DailyCheckIn.oneLine`과 `PastEncounter.note` 분리 |
| 매칭 노출 | 매칭 자체가 새로운 숙제가 될 수 있음 | 사용자가 직접 시작할 때만 매칭 |
| 매칭 범위 | 도움 방식·공개 범위를 사용자가 통제하지 못함 | 매칭 시작 전 한 단계 선택 |
| 연결 후 빈 화면 | 수락 후 무엇을 하는지 불명확 | 검토 가능한 첫 인사와 중계 전달 추가 |
| 비응답 해석 | 상대의 무응답을 사용자의 실패로 오해 가능 | 실패·미달성 상태를 만들지 않고 조용한 종료 |

QA 결론: **설계 통과 조건은 충족했지만, S3~S6 구현 전에는 실제 사람 간 연결을 활성화하지 않는다.**

## 11. 구현 순서

1. 오늘/묵상기록지의 추천 성구 + 과거 기록 연결 장면 정리
2. 반응 모달과 다음 성구 흐름 안정화
3. `CompanionProfile` 및 공개 범위 설정
